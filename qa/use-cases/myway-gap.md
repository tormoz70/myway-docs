## Что изменилось в этом ревью

Stage 2 закрыл **ядро** четырёх отраслевых болей. В прошлой версии gap это уже частично отражалось в таблице UC, но **Must-бэклог и заметки ролей** всё ещё читались как «надо строить с нуля».

| Тема | Было в Must / заметках | Сейчас в продукте | Остаток |
|------|------------------------|-------------------|---------|
| Отработка | Must #3 | `makeup_of_enrollment_id` + `skip_visit_debit`; модалка в посещаемости; карточка «Нужна отработка» на главной ADMIN | Не отдельный тип абонемента |
| Замена преподавателя | Must #4 | `schedule_occurrence_overrides`; SHIFT_SWAP → override; email enrolled/waitlist | Нет SMS/push; нет payroll замены |
| Воронка пробное→абонемент | Must #1 | `sales_pipeline_items`; страница «Воронка»; KPI на главной OWNER/ADMIN | Нет обзвона, телефонии, SLA |
| Семья / родитель | Must #2 | `family_accounts` + `actingAsUserId`; карточка «Семья» у STUDENT | Нет роли PARENT; оплата ребёнка — через guardian |
| Флаг финансов админу | Must #5 | OWNER: Настройки → **Доступ** → `financeReportForAdmin` | — |
| Абонементы заканчиваются | Must #6 | Главная OWNER/ADMIN + фильтр `expiring-soon` + email `PASS_EXPIRING` | Нет SMS «сегодня» |

### Правки после прогона симулятора (2026-08-22)

Симулятор на ручном стенде нашёл два дефекта в уже закрытых, как считалось, потоках:

| UC | Что было | Правка |
|----|----------|--------|
| UC-CLIENT-01 / 02 | «Моё расписание» строилось на `GET /schedule/entries?studentId=me`, а фильтр учитывал только плановый ростер `schedule_entry_students`. Занятие, на которое студент записался онлайн, ему не показывалось — вместе с кнопкой отмены | студент считается участником и по своей активной записи |
| UC-SALES-02 | имя и почта лида заполнялись только из связанного пользователя, у заявки с сайта аккаунта нет — в колонке «Клиент» стоял прочерк | имя из профиля, при его отсутствии — из заявки; телефон заявки второй строкой |

Оба потока раньше числились закрытыми, потому что автотесты на них уходили в `skip` «нет активной
записи для отмены» — то есть skip прятал дефект. Отсюда правило симулятора: незасеянная фикстура —
падение, а не пропуск (см. [simulator.md](./simulator.md)).

## Маппинг отраслевых ролей на MyWay

| Отраслевая роль | MyWay | Разница |
|-----------------|-------|---------|
| Владелец | `OWNER` | Совпадает |
| Управляющий филиалом | `OWNER` или `ADMIN` | Нет отдельной роли; финансы ADMIN — по флагу `financeReportForAdmin` (UI у OWNER) |
| Старший администратор | `ADMIN` (+ флаг) | Нет иерархии админов, нет «lead shift» |
| Администратор ресепшена | `ADMIN` | Операции + воронка/KPI на главной; касса смены и обзвон — вне продукта |
| Менеджер по продажам | `ADMIN` | Воронка есть; нет задач обзвона и телефонии |
| Преподаватель | `INSTRUCTOR` | Совпадает; payroll preview — частично |
| Ассистент преподавателя | — | **Нет роли** |
| Ученик (взрослый) | `STUDENT` | В продукте клиент = STUDENT |
| Родитель | `STUDENT` (guardian) | **Нет роли PARENT**; `family_accounts` (GUARDIAN\|CHILD) + «Смотреть как ребёнок» |
| Арендатор зала | `SUB_TENANT` | Совпадает; без QR-прохода |
| Уборщица | `CLEANER` | График уборки — частично (расписание, не чек-лист) |
| Маркетолог | — | Вне RBAC |
| Бухгалтер | — | Экспорт 1С — есть для OWNER/ADMIN |
| Оператор платформы | `SUPER_ADMIN`, `SUPER_USER` | Вне студии |

### Намеренно не копируем

| Тема | Причина |
|------|---------|
| Десятки permission groups (Mindbody) | Достаточно фиксированных ролей + 1–2 флага |
| Складской учёт (YCLIENTS) | Не ядро MyWay |
| Два типа входа staff vs consumer (Mindbody) | Один `User` на человека + membership в org; не второй «клиентский» логин для сотрудника |
| Instagram DM интеграция | Интеграция, не доменная логика |
| Отдельная роль PARENT | Семья через guardian STUDENT; роль плодит RBAC без новой операционной модели |

**Staff vs consumer (Mindbody vs MyWay):** у каждого человека в MyWay **свой** аккаунт (`User`, уникальный email, свой пароль) — не «один логин на всех». Разница с Mindbody в **модели**: там сотрудник может иметь **staff login** (рабочий кабинет) и отдельный **consumer / Mindbody account** (запись на занятие как клиент), иногда на одном email, но как разные типы входа. В MyWay — один вход и одна сессия; роль в студии задаётся membership (`user_org_roles`: user + organization + role). Повторный invite существующего email только добавляет membership, без второго пароля. На одну организацию — одна роль на user (преподаватель «как клиент» в той же студии — не через второй логин, а через другую роль/membership или ручную запису).
