## Маппинг отраслевых ролей на MyWay

| Отраслевая роль | MyWay | Разница |
|-----------------|-------|---------|
| Владелец | `OWNER` | Совпадает |
| Управляющий филиалом | `OWNER` или `ADMIN` | Нет отдельной роли; финансы ADMIN — по флагу `financeReportForAdmin` |
| Старший администратор | `ADMIN` (+ флаг) | Нет иерархии админов, нет «lead shift» |
| Администратор ресепшена | `ADMIN` | Совпадает по операциям; продажи/KPI — вне продукта |
| Менеджер по продажам | `ADMIN` | Нет CRM лидов и задач обзвона |
| Преподаватель | `INSTRUCTOR` | Совпадает; payroll preview — частично |
| Ассистент преподавателя | — | **Нет роли** |
| Ученик (взрослый) | `STUDENT` | В продукте клиент = STUDENT |
| Родитель | — / `STUDENT` | **Нет роли**; часто один аккаунт на семью |
| Арендатор зала | `SUB_TENANT` | Совпадает; без QR-прохода |
| Уборщица | `CLEANER` | График уборки — частично (расписание, не чек-лист) |

### Намеренно не копируем

| Тема | Причина |
|------|---------|
| Десятки permission groups (Mindbody) | Достаточно фиксированных ролей + 1–2 флага |
| Складской учёт (YCLIENTS) | Не ядро MyWay |
| Два типа входа staff vs consumer (Mindbody) | Один `User` на человека + membership в org; не второй «клиентский» логин для сотрудника |
| Instagram DM интеграция | Интеграция, не доменная логика |

**Staff vs consumer (Mindbody vs MyWay):** у каждого человека в MyWay **свой** аккаунт (`User`, уникальный email, свой пароль) — не «один логин на всех». Разница с Mindbody в **модели**: там сотрудник может иметь **staff login** (рабочий кабинет) и отдельный **consumer / Mindbody account** (запись на занятие как клиент), иногда на одном email, но как разные типы входа. В MyWay — один вход и одна сессия; роль в студии задаётся membership (`user_org_roles`: user + organization + role). Повторный invite существующего email только добавляет membership, без второго пароля. На одну организацию — одна роль на user (преподаватель «как клиент» в той же студии — не через второй логин, а через другую роль/membership или ручную запису).

## Покрытие manual test stand

Скрипт `seed_manual_test_stand.py` **не** цель этого этапа; ориентировочно:

| UC cluster | Данные на стенде |
|------------|------------------|
| OWNER/ADMIN расписание, пропуска, клиенты | Да (после S-OWN-03) |
| SUB_TENANT субаренда | Да (3 студии, sublease) |
| Финансы / оборот | Да (`manual_stand_lifecycle.py` finance seed) |
| Waitlist | Нужны переполненные группы — **не по умолчанию** |
| Лиды / воронка | **Нет** |
| Родитель / несколько детей | **Нет** |
| Касса / смена | **Нет** |

Подробные сценарии ролей: [manual-stand-role-scenarios.md](../manual-testing/manual-stand-role-scenarios.md).
