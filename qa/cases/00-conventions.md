# Соглашения и формат тест-кейсов

## 1. Окружение и предусловия

- **Frontend:** React + TypeScript + Ant Design, маршруты под префиксом `/go`.
- **Backend:** Spring Boot, базовый URL API — `/api`.
- **БД:** PostgreSQL. **Проверка «сохранено в базу»** выполняется одним из способов:
  1. **UI-reload (основной способ):** закрыть и снова открыть форму редактирования / обновить
     страницу (F5) и убедиться, что значение пришло из бэкенда (а не из локального состояния).
  2. **API-проверка:** выполнить соответствующий `GET`-запрос (см. эндпоинт в шапке формы) и
     сверить значение поля в ответе.
  3. **Прямой SQL (по необходимости):** `docker compose exec postgres psql -U myway -d myway -c "..."`.
- Поднять локальный стенд можно скриптом из навыка `run-dev-stack` (Docker Postgres/Redis/MinIO +
  Spring Boot `:8080` + Vite `:5173`).

## 2. Тестовые учётные записи

Для полного прогона нужны аккаунты всех ролей в одном тестовом тенанте `:slug` плюс операторы платформы:

| Роль | Как получить |
|------|--------------|
| `SUPER_ADMIN` | Bootstrap-учётка платформы. |
| `SUPER_USER` | Создаётся SUPER_ADMIN на вкладке «Платформа → Операторы». |
| `OWNER` | Регистрация студии на `/go/register`. |
| `ADMIN` | Приглашение из **«Сотрудники»** → «Администраторы». |
| `CLEANER` | Приглашение из **«Сотрудники»** → «Администраторы», роль «Уборщица». |
| `SUB_TENANT` | Приглашение из **«Клиенты»** или заявка. |
| `INSTRUCTOR` | Приглашение из **«Сотрудники»** → «Преподаватели» или `/go/:slug/join/instructor`. |
| `STUDENT` | Приглашение из **«Клиенты»** или `/go/:slug/join/student`. |

Каждый аккаунт должен иметь **подтверждённый email**, иначе действует баннер «Email не подтверждён»
и сохранение изменений блокируется на бэкенде (отдельная серия проверок, см. §6).

## 3. Формат тест-кейса

Каждый тест-кейс оформлен по шаблону:

> **TC-<РОЛЬ>-<ФОРМА>-NN — Заголовок**
> - **Предусловие:** состояние системы/данных до теста.
> - **Шаги:** пронумерованные действия.
> - **Ожидаемый результат:** что должно произойти в UI **и** что должно сохраниться/прочитаться из БД.
> - **Проверка БД/бизнес-логики:** конкретное поле/эндпоинт/SQL, по которому подтверждается результат.

Типы проверок, которые встречаются в кейсах:

- **[Кнопка]** — действие реально выполняет бизнес-операцию (а не просто закрывает модалку без ошибки).
- **[Сохранение]** — значение поля/списка попадает в БД и подтягивается обратно при повторном открытии.
- **[Отображение]** — информационное поле или ячейка таблицы соответствует данным из БД/бизнес-логике.
- **[Валидация]** — клиентская/серверная проверка отклоняет некорректный ввод.
- **[Доступ]** — поведение, зависящее от роли (видимость, блокировки, 403).

## 4. Соглашение о статусе доступа

В тест-кейсах используется явное разграничение:

- **UI скрывает действие** — кнопки/вкладки/поля не отображаются для роли.
- **UI показывает, backend запрещает (403)** — важный класс дефектов: для ряда форм фронтенд
  не прячет кнопки от ролей без прав (расписание, залы, биллинг, новости, заявки и т.д.), и действие
  должно отклоняться сервером. Такие кейсы помечены **[Доступ/403]**.

## 5. Общий формат данных в UI

- Деньги: абонементы/финансы — в копейках в API (`*Minor`), в UI часто рубли. Биллинг/счета/расходы —
  в рублях напрямую. **Поурочные тарифные планы предмета удалены** (миграция V63); не проверять
  `finance/tariff-charges` и кнопки «Тарифные планы» у предмета как живую фичу.
- Даты в таблицах: `DD.MM.YYYY` или `DD.MM.YYYY HH:mm`.
- Статусы выводятся локализованными тегами; их значения должны совпадать со статусом сущности в БД.

## 6. Сквозные проверки (для всех ролей и форм)

Эти проверки следует прогонять как отдельную серию поверх любой формы с сохранением:

- **CONV-EMAIL-UNVERIFIED:** при `user.emailVerified === false` отображается баннер; любое
  сохранение (`POST/PUT/PATCH/DELETE`) должно отклоняться бэкендом, несмотря на то что кнопки активны.
- **CONV-RELOAD:** после любого успешного сохранения — F5/повторное открытие формы возвращает
  именно сохранённое значение из БД.
- **CONV-TENANT-ISOLATION:** пользователь одного тенанта не видит и не может менять данные другого
  тенанта (смена `:slug` в URL не-оператором редиректит на свой дашборд — `ProtectedRoute`).
- **CONV-AUTH:** при истёкшем/отсутствующем токене любая защищённая форма редиректит на `/go/login`.
- **CONV-TOAST:** успешные операции показывают success-тост с корректным текстом; ошибки — текст из
  `response.data.message` либо специфичный фолбэк.

## 7. Карта форм → эндпоинты (справочно)

Полная карта хуков и эндпоинтов приведена внутри каждого ролевого файла в шапке соответствующей
формы. Базовые группы:

- Auth: `/api/auth/*`
- Public site: `/api/public/*`
- Subjects: `/api/subjects/*`
- Schedule: `/api/schedule/entries*`, `/api/schedule/entries/{id}/attendance`
- Premises / halls: `/api/premises/*`, `/api/halls/*` (копирование `POST /halls/{id}/copy`, перенос `POST /halls/{id}/move`, восстановление `POST /premises|halls/{id}/restore`; удаление = архивация `isActive=false`)
- Access: `/api/access/*`, `/api/passes/*`
- Billing: `/api/billing/*`
- Finance: `/api/finance/*`
- Sublease: `/api/sublease/*`
- Export: `/api/export/1c`
- Organizations/members: `/api/organizations/{orgId}/*`
- Platform: `/api/platform/*`
- Account: `/api/account/privacy/*`, `/api/auth/profile`, `/api/auth/change-password`
