# Тест-кейсы: OWNER (владелец студии)

Канонические ID: `TC-OWNER-*`. Старые ярлыки Playwright `TC-OWN-*` — только в [coverage.md](../coverage.md).

Полный доступ ко всем разделам своего тенанта. Финансы доступны, если платформенный флаг
`finance.turnoverReport !== false` (для OWNER по умолчанию включено). Все формы — под `/go/:slug/manage/...`.

Сквозные проверки (`CONV-*`) из `00-conventions.md` применимы к каждой форме с сохранением.

---

## Форма: Дашборд тенанта (`/manage/dashboard`)

Эндпоинты: `POST /platform/messages/to-super-admin`, `GET /platform/messages/inbox` (только OWNER).

### TC-OWNER-DASH-01 — [Отображение] KPI-карточки
- **Ожидаемый результат:** карточки «Записей сегодня/Активных пропусков/Неоплаченных счетов/Бронирований субаренды»
  отображаются (на текущей реализации значения = 0, плейсхолдер). Зафиксировать как ожидаемое.

### TC-OWNER-DASH-02 — [Кнопка] Быстрые действия
- **Шаги:** нажать «Новое занятие», «Продать абонемент», «Регистрация входа», «Создать бронирование».
- **Ожидаемый результат:** переходы на `schedule?action=new`, `finance/pass-templates`, `gate`, `sublease`.

### TC-OWNER-DASH-03 — [Кнопка][Сохранение] Связь с поддержкой (SUPER_ADMIN)
- **Шаги:** заполнить Тему и Сообщение → отправить.
- **Ожидаемый результат:** `POST /platform/messages/to-super-admin`; сообщение сохранено/доставлено; тост «Сообщение отправлено».
- **Валидация:** пустые/пробельные поля отклоняются.

### TC-OWNER-DASH-04 — [Отображение] Входящие сообщения
- **Ожидаемый результат:** таблица входящих (`GET /platform/messages/inbox`): Направление (тег), Тема, Сообщение,
  Доставка (локализованный `deliveryStatus`), Создано — из БД. Раздел виден только OWNER.

## Форма: Предметы (`/manage/subjects`)

Эндпоинты: `GET/POST /subjects`, `PUT/DELETE /subjects/{id}`, `PATCH /subjects/{id}/catalog-active`,
`GET /subjects/{id}`, члены `GET /organizations/{orgId}/members`.

### TC-OWNER-SUBJ-01 — [Отображение] Таблица предметов
- **Ожидаемый результат:** колонки Название (`name`), Каталог (Switch для OWNER), Преподаватели (`instructorIds.length`),
  Ученики (`studentIds.length`), Действия — соответствуют БД.

### TC-OWNER-SUBJ-02 — [Кнопка][Сохранение] Создание предмета
- **Шаги:** «Новый предмет» → Название, Описание, Мин/Макс учеников, Преподаватели → «Создать».
- **Ожидаемый результат:** `POST /subjects`; предмет создан в БД (`studentAssignments: []`); тост; таблица обновлена.
- **Проверка [Сохранение]:** открыть предмет на редактирование — поля = сохранённым (`name`, `description`, `minStudents`, `maxStudents`, `instructorIds`).

### TC-OWNER-SUBJ-03 — [Сохранение] Редактирование предмета
- **Шаги:** «Редактировать» → изменить поля → «Сохранить».
- **Ожидаемый результат:** `PUT /subjects/{id}`; существующие зачисления сохраняются; изменения видны после reopen/F5.

### TC-OWNER-SUBJ-03A — [Кнопка][Сохранение] HTML-описание предмета
- **Предусловие:** предмет создан; MinIO доступен.
- **Шаги:** «Редактировать» → в секции «HTML-описание» ввести текст, загрузить изображение, «Вставить в текст» → «Сохранить HTML-описание».
- **Ожидаемый результат:** `PUT /api/content/SUBJECT/{id}/description`; `POST /api/content/SUBJECT/{id}/images`; plain `description` обновлён (strip HTML); на публичной форме заявки видно `renderedDescription`.

### TC-OWNER-SUBJ-04 — [Переключатель][Сохранение] Каталог активен/черновик
- **Шаги:** переключить Switch «Каталог».
- **Ожидаемый результат:** `PATCH /subjects/{id}/catalog-active {catalogActive}`; тост «введён в эксплуатацию»/«скрыт из каталога».
- **Проверка бизнес-логики:** при `catalogActive=false` предмет исчезает из публичного каталога (`/go/:slug`) и из селектора предметов в расписании.

### TC-OWNER-SUBJ-05 — [Кнопка] Удаление предмета
- **Шаги:** «Удалить» → подтвердить.
- **Ожидаемый результат:** `DELETE /subjects/{id}`; предмет удалён, связи с занятиями сняты.

### TC-OWNER-SUBJ-06 — [Упрощение] Тарифные планы удалены
- **Ожидаемый результат:** в разделе «Предметы» больше нет операций тарифных планов.
- **Пояснение:** оплата занятий оформляется через «Пропуска» (`SINGLE`/`VISIT_PACK`/`UNLIMITED`/`COMBO`).

### TC-OWNER-SUBJ-09 — [Кнопка][Сохранение] Зачисление учеников
- **Шаги:** выбрать учеников предмета без привязки к тарифу.
- **Ожидаемый результат:** изменения сохраняются через `PUT /subjects/{id}` с `studentAssignments: [{studentUserId}]`.

## Форма: Расписание (`/manage/schedule`) + EntryForm + AttendanceEditor

Эндпоинты: `GET /schedule/entries?hallId&from&to`, `POST /schedule/entries`, `PUT/DELETE /schedule/entries/{id}`,
посещаемость `GET/PUT /schedule/entries/{id}/attendance`.

### TC-OWNER-SCHED-01 — [Отображение] Календарь и фильтры
- **Шаги:** переключать День/Неделя/Месяц, листать ←/→, выбрать дату, фильтр по залу.
- **Ожидаемый результат:** записи в диапазоне дат соответствуют БД; цвет блока = `entry.color`→`hall.color`→дефолт; фильтр по `hallId` корректен.

### TC-OWNER-SCHED-02 — [Кнопка][Сохранение] Создание занятия (CLASS)
- **Шаги:** «Новая запись» (или клик пустого слота) → Зал, Тип `CLASS`, Предмет, Преподаватели, дата/время, повторение, цвет, ученики → «Создать».
- **Ожидаемый результат:** `POST /schedule/entries`; `title` = название предмета; `startTime`/`endTime` — ISO из дат+времени;
  сохранены `recurrenceMode`/`recurrence`, `weekDays`/`monthDays`, `studentIds`, `instructorIds`, `color`; тост «Запись создана».
- **Проверка [Сохранение]:** открыть запись на редактирование — все поля = сохранённым; запись видна в публичном расписании (если в окне 14 дней).

### TC-OWNER-SCHED-03 — [Сохранение] Создание аренды/блокировки (не CLASS)
- **Шаги:** тип `RENT`/`MAINTENANCE`/`BLOCKED` → требуется поле «Название»; предмет не требуется → сохранить.
- **Ожидаемый результат:** запись сохранена с введённым `title`, без `subjectId`.

### TC-OWNER-SCHED-04 — [Выпадающий список] Фильтрация преподавателей по предмету
- **Шаги:** для CLASS выбрать предмет, у которого заданы `instructorIds`.
- **Ожидаемый результат:** в «Преподаватели (план)» доступны только преподаватели предмета; ранее выбранные «лишние» удаляются.

### TC-OWNER-SCHED-05 — [Валидация] Время/даты/повторение
- **Шаги:** задать дату окончания раньше начала; время «по» раньше «с» в один день; WEEKLY без дней недели; MONTHLY без чисел.
- **Ожидаемый результат:** соответствующие ошибки валидации; некорректные комбинации не сохраняются.

### TC-OWNER-SCHED-06 — [Кнопка] Удаление записи
- **Шаги:** открыть запись → «Удалить».
- **Ожидаемый результат:** `DELETE /schedule/entries/{id}`; запись удалена; тост. (Внимание: подтверждения нет — риск случайного удаления.)

### TC-OWNER-SCHED-07 — [Сохранение] Вкладка «Ученики»
- **Шаги:** при редактировании CLASS добавить/удалить учеников → сохранить запись.
- **Ожидаемый результат:** `studentIds` сохраняются вместе с записью (отдельного запроса нет); reopen показывает актуальный список.

### TC-OWNER-SCHED-08 — [Кнопка][Сохранение] Посещаемость занятия (CLASS, edit)
- **Предусловие:** редактируется существующее CLASS-занятие; вкладка «Факт посещаемости».
- **Шаги:** переключить Switch присутствия для преподавателей/учеников → «Сохранить».
- **Ожидаемый результат:** `PUT /schedule/entries/{id}/attendance {occurrenceStart, occurrenceEnd, records:[{userId,participantRole,present}]}`;
  тост «Посещаемость сохранена».
- **Проверка [Сохранение]:** `GET .../attendance` (reopen) возвращает плановых участников с наложенными фактическими отметками.
- **Проверка бизнес-логики:** факт посещаемости влияет на списание/учёт использования пропуска (абонементная модель).

## Форма: Помещения и залы (`/manage/rooms`)

Модель: **помещение → залы**. Адрес и общая площадь — на помещении; тип, ставка, цвет, площадь зала — на зале.
Удаление = **архивация** (`isActive=false`), не физическое удаление из БД.

Эндпоинты:
- Помещения: `GET/POST /premises`, `PUT/DELETE /premises/{id}`, `GET /premises?archived=true`, `POST /premises/{id}/restore`
- Залы: `GET/POST /halls`, `PUT/DELETE /halls/{id}`, `POST /halls/{id}/copy`, `POST /halls/{id}/move`, `GET /halls?archived=true`, `POST /halls/{id}/restore`

### TC-OWNER-PREM-01 — [Отображение] Master-detail помещения → залы
- **Ожидаемый результат:** таблица помещений (Название, Адрес, Площадь, число залов); раскрытие строки показывает залы этого помещения; данные из БД.

### TC-OWNER-PREM-02 — [Кнопка][Сохранение] Создание помещения
- **Шаги:** «Добавить помещение» → Название (обяз.), Адрес, Общая площадь (м²), Описание → сохранить.
- **Ожидаемый результат:** `POST /premises`; помещение создано; тост «Помещение создано».
- **Проверка [Сохранение]:** «Изменить» подгружает сохранённые поля.

### TC-OWNER-PREM-03 — [Сохранение] Редактирование помещения
- **Ожидаемый результат:** `PUT /premises/{id}`; изменения сохранены и видны после reopen/F5.

### TC-OWNER-PREM-04 — [Кнопка] Архивация помещения (каскад по залам)
- **Предусловие:** в помещении есть один или несколько активных залов.
- **Шаги:** «Удалить» у помещения → подтвердить (Popconfirm про архив помещения и всех залов).
- **Ожидаемый результат:** `DELETE /premises/{id}`; помещение и **все** его залы получают `isActive=false`; тост «Помещение и залы перенесены в архив».
- **Проверка [Отображение]:** помещение исчезает из основной таблицы; появляется в блоке «Архив».

### TC-OWNER-PREM-05 — [Кнопка] Восстановление помещения (каскад по залам)
- **Предусловие:** помещение в архиве (см. `TC-OWNER-PREM-04`).
- **Шаги:** в блоке «Архив» → «Восстановить» у помещения.
- **Ожидаемый результат:** `POST /premises/{id}/restore`; помещение и **все** привязанные залы снова `isActive=true`; тост «Помещение и залы восстановлены».
- **Проверка [Сохранение]:** F5 → помещение и залы снова в основной таблице.

### TC-OWNER-HALL-01 — [Кнопка][Сохранение] Создание зала в помещении
- **Шаги:** у помещения «Зал» → Название, Тип, Площадь (≥0), Стоимость/час (≥0), Описание, Цвет → сохранить.
- **Ожидаемый результат:** `POST /halls {premiseId, ...}`; зал создан; тост «Зал создан».
- **Проверка [Сохранение]:** «Изменить» подгружает все сохранённые поля, включая цвет.

### TC-OWNER-HALL-02 — [Сохранение] Редактирование зала
- **Ожидаемый результат:** `PUT /halls/{id}`; изменения сохранены и видны после reopen/F5.

### TC-OWNER-HALL-03 — [Валидация] Сумма площадей залов ≤ площади помещения
- **Предусловие:** у помещения задана общая площадь.
- **Шаги:** создать/изменить зал так, чтобы сумма активных площадей превысила площадь помещения.
- **Ожидаемый результат:** backend 400 с сообщением о превышении; сохранение не выполняется.

### TC-OWNER-HALL-04 — [Кнопка] Архивация зала (не последнего)
- **Предусловие:** в помещении ≥2 активных зала.
- **Шаги:** «Удалить» у зала → подтвердить.
- **Ожидаемый результат:** `DELETE /halls/{id}`; зал `isActive=false`; тост «Зал перенесён в архив»; зал исчезает из раскрытой строки; при необходимости виден в «Архив» (если помещение активно).

### TC-OWNER-HALL-05 — [Валидация] Нельзя архивировать последний зал
- **Предусловие:** в активном помещении ровно один активный зал.
- **Шаги:** попытаться «Удалить» этот зал.
- **Ожидаемый результат:** backend 409 «Нельзя удалить последний зал в помещении»; тост с текстом ошибки; зал остаётся активным.

### TC-OWNER-HALL-06 — [Кнопка] Восстановление зала из архива
- **Предусловие:** зал архивирован отдельно (`TC-OWNER-HALL-04`), помещение активно.
- **Шаги:** в блоке «Архив» → «Восстановить» у зала.
- **Ожидаемый результат:** `POST /halls/{id}/restore`; зал снова активен; тост «Зал восстановлен».
- **Валидация:** если помещение в архиве — восстановление зала отклоняется («Сначала восстановите помещение»).

### TC-OWNER-HALL-07 — [Кнопка][Сохранение] Копирование зала
- **Шаги:** у зала «Копировать» → имя нового зала, целевое помещение → подтвердить.
- **Ожидаемый результат:** `POST /halls/{id}/copy`; создан **новый** зал (новый UUID) с копией атрибутов; расписание/субаренда/пропуска **не** копируются; тост «Зал скопирован».

### TC-OWNER-HALL-08 — [Кнопка][Сохранение] Перенос зала в другое помещение
- **Предусловие:** в исходном помещении ≥2 активных зала (нельзя перенести последний).
- **Шаги:** «Перенести» → выбрать целевое помещение → подтвердить.
- **Ожидаемый результат:** `POST /halls/{id}/move`; UUID зала сохранён; `premise_id` изменён; расписание/субаренда/check-in по `hall_id` не ломаются; проверка суммы площадей в целевом помещении.

> **Устаревшие идентификаторы:** `TC-OWNER-ROOM-01..04` заменены на `TC-OWNER-PREM-*` и `TC-OWNER-HALL-*`.

### TC-OWNER-DIR-01 — [Кнопка][Сохранение] Справочник направлений
- **Шаги:** `/manage/directions` → создать направление с HTML-описанием на вкладке «Описание».
- **Ожидаемый результат:** `POST/PUT /api/directions`; контент через `/api/content/DIRECTION/{id}/description`.

### TC-OWNER-AGE-01 — [Кнопка][Сохранение] Возрастные категории
- **Шаги:** `/manage/age-categories` → создать категорию «Дети» с описанием.
- **Ожидаемый результат:** `POST /api/age-categories`; запись в списке.

### TC-OWNER-SUBJECT-LINK-01 — Связь предмета с направлением и возрастом
- **Шаги:** `/manage/subjects` → редактировать предмет → выбрать направление и возрастную категорию.
- **Ожидаемый результат:** в таблице отображаются выбранные значения; `PUT /api/subjects/{id}` с `directionId`, `ageCategoryId`.

### TC-OWNER-HALL-ATTR-01 — Атрибуты зала (оборудование, интерьер, высота)
- **Шаги:** `/manage/rooms` → редактировать зал → заполнить оборудование, интерьер, высоту потолков.
- **Ожидаемый результат:** `PUT /api/halls/{id}`; поля сохраняются и отдаются в публичном `premises-catalog`.

## Форма: Пропуска и абонементы (`/manage/access`, шаблоны — `/manage/finance/pass-templates`)

Эндпоинты: шаблоны `/access/templates`, пропуска `/access/passes` (+ freeze/revoke/unfreeze), `POST /passes/{id}/mark-paid`,
`POST /passes/{id}/mark-refunded`, `POST /access/check-in`, `GET /access/check-in/search`, `GET /access/logs`,
станция `GET /access/gate/display|status` (UI станции — `/manage/gate`).

### TC-OWNER-ACCESS-01 — [Кнопка][Сохранение] Создание шаблона пропуска
- **Шаги:** **Финансы → Абонементы** → «Создать абонемент» → Название, Тип (**Разовое посещение** / **Пакет посещений** / **Безлимит**), Длительность, Цена, Макс. визитов;
  опционально: **Роль держателя**, **Область доступа** (`ALL` / `PREMISES` / `HALLS`), списки помещений/залов, **Контроль графика** (Switch) → создать.
- **Ожидаемый результат:** `POST /access/templates` с полями `targetRole`, `accessScope`, `allowedPremiseIds`, `allowedHallIds`, `scheduleEnforcement`; шаблон в БД; тост «Шаблон создан».
- **Проверка [Отображение]:** в таблице тип локализован, цена `{price} ₽`, макс. визитов = `maxVisits` или `∞`.
- **Проверка бизнес-логики:** недопустимые комбинации роль/scope отклоняются backend (напр. OWNER → только `ALL` + без контроля графика).

### TC-OWNER-ACCESS-02 — [Кнопка][Сохранение] Выдача пропуска
- **Предусловие:** есть хотя бы один шаблон (иначе кнопка disabled).
- **Шаги:** **«Продать абонемент»** → выбрать держателя и шаблон → подтвердить.
- **Ожидаемый результат:** `POST /access/passes {templateId, holderId}`; пропуск создан со статусом `ACTIVE`, сгенерирован `qrCodeToken`; на пропуске сохранён **snapshot** политики шаблона; тост «Пропуск выдан».
- **Проверка [Отображение]:** пропуск появляется в «Активные пропуска» с владельцем (`members.fullName/email`), кодом (маскирован), сроками, визитами, статусом.

### TC-OWNER-ACCESS-03 — [Кнопка] Заморозка/разморозка/отзыв
- **Шаги:** у ACTIVE «Заморозить»; у FROZEN «Разморозить»; у ACTIVE «Отозвать».
- **Ожидаемый результат:** `PUT .../freeze|unfreeze|revoke`; статус в БД меняется (`FROZEN`/`ACTIVE`/`REVOKED`); тосты соответствуют.
- **Проверка бизнес-логики:** замороженный/отозванный пропуск не проходит регистрацию входа.

### TC-OWNER-ACCESS-04 — [Кнопка][Сохранение] Отметка оплаты
- **Шаги:** у ACTIVE без оплаты «Отметить оплату» → сумма (≥0.01) и дата → подтвердить.
- **Ожидаемый результат:** `POST /passes/{id}/mark-paid`; `paidAt`/`paidAmount` сохранены; колонка «Оплата» обновлена.
- **Проверка бизнес-логики:** доход попадает в категорию `INCOME_PASSES_DROP_IN` (SINGLE) или `INCOME_PASSES_SUBSCRIPTION` и виден в отчёте оборота.

### TC-OWNER-USERS-03 — [Сохранение] Редактирование участника
- **Шаги:** «Изменить» → email/имя/фамилия; для INSTRUCTOR/ADMIN — переключатель публичного профиля, био; предметы (на странице преподавателей) → «Сохранить».
- **Ожидаемый результат:** `PUT .../members/{id}` (+ `publicProfileEnabled`/`publicBio`); при INSTRUCTOR-варианте — синхронизация привязки предметов через `PUT /subjects/{id}`; для staff при изменении email — письмо с новым транспортным паролем (см. TC-OWNER-USERS-02A).
- **Проверка [Сохранение]:** reopen показывает сохранённые поля; публичный профиль виден/скрыт на `/go/:slug/teachers`.

### TC-OWNER-USERS-04 — [Выпадающий список][Сохранение] Смена роли
- **Шаги:** в модалке изменить «Роль» → «Сохранить».
- **Ожидаемый результат:** `PUT .../members/{id}/role {role}`; роль сохранена.
- **Проверка [Доступ]:** для себя селект роли disabled; удалить себя нельзя.

### TC-OWNER-USERS-05 — [Кнопка] Удаление участника
- **Шаги:** «Удалить» (не себя) → подтвердить.
- **Ожидаемый результат:** `DELETE .../members/{userId}`; участник удалён; тост «Пользователь удален».

## Форма: Настройки (`/manage/settings`)

Эндпоинты: `PUT /organizations/{orgId}`, `PATCH /organizations/{orgId}/public-site`, члены/владелец `.../members*`,
`POST /auth/change-password`.

### TC-OWNER-SET-ORG-01 — [Сохранение] Вкладка «Организация»
- **Шаги:** «Редактировать» → Название, Станционный QR: смена кода (10–300с), Окно расписания (5–120 мин) → «Сохранить».
- **Ожидаемый результат:** `PUT /organizations/{orgId}`; данные сохранены; `authStore.organization` обновлён; тост «Организация обновлена».
- **Проверка [Сохранение]:** F5 → поля = сохранённым; gate-поля видны только OWNER/ADMIN.

### TC-OWNER-SET-PUB-01 — [Сохранение] Вкладка «Публичный сайт»
- **Шаги:** изменить Описание, Контактный телефон/email, Адрес, Соцсети (JSON), переключатель «Заявки требуют подтверждения» → «Сохранить».
- **Ожидаемый результат:** `PATCH /organizations/{orgId}/public-site`; значения сохранены; тост; `['org','by-slug',slug]` invalidate.
- **Проверка бизнес-логики:** при включённом переключателе публичные заявки создают аккаунты со статусом PENDING (см. Заявки); изменения видны на `/go/:slug`.

### TC-OWNER-SET-ADM-01 — Вкладка «Администраторы» (устарело)
- **Ожидаемый результат:** вкладки в Настройках нет. Администраторы и клинер — **Кадры → Сотрудники**.

### TC-OWNER-SET-OWN-01 — [Сохранение] Вкладка «Владелец»
- **Шаги:** «Редактировать» → email/имя/фамилия владельца → «Сохранить».
- **Ожидаемый результат:** `PUT /organizations/{orgId}/members/{owner.id}`; данные владельца сохранены; если текущий пользователь = владелец, синхронизируется `authStore.user`.

### TC-OWNER-SET-SEC-01 — [Кнопка][Валидация] Вкладка «Безопасность»
- **Шаги:** Текущий пароль, Новый (≥8, zxcvbn≥2), Подтверждение → «Сменить пароль».
- **Ожидаемый результат:** `POST /auth/change-password`; пароль изменён (проверить повторным входом); тост «Пароль успешно изменен».
- **Валидация:** несовпадение подтверждения / слабый пароль отклоняются.

## Форма: Личный кабинет (`/manage/me/*`)

`POST .../admin-work/marks`, `POST /access/gate/scan`, `POST /access/check-in`.

### TC-OWNER-ME-01 — [Отображение] Главная ЛК
- **Ожидаемый результат:** карточки «Моё расписание», «График работы (администратор)», «Отметиться по QR» (для OWNER видны все три).

- **Шаги:** открыть «Моё расписание», листать недели.
- **Ожидаемый результат:** для OWNER —週 без user-фильтра (`GET /schedule/entries?from&to`); записи соответствуют БД (заголовок/время/зал).

### TC-OWNER-ME-03 — [Кнопка][Сохранение] График работы — отметка факта
- **Шаги:** на «График работы» переключить Switch «Факт» в строке дня.
- **Ожидаемый результат:** `POST .../admin-work/marks {adminUserId, workDate, present}`; отметка сохранена; тост «Сохранено».

- **Ожидаемый результат:** `POST /access/gate/scan {raw}`; success → «Вход зарегистрирован»; deny-коды (INVALID_CODE/NO_PASS/NO_SLOT/…) отображаются понятными сообщениями; камера останавливается.

- **Шаги:** ввести токен личного пропуска → «Отметиться».
- **Ожидаемый результат:** `POST /access/check-in {qrCodeToken}`; success «Посещение зарегистрировано»; поле очищается.
